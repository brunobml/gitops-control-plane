## 1. Executive Summary

This lab works from end to end, and the architecture is mostly sound. A Git push reaches kro instances on two spokes, which provision SQS queues (with DLQs and redrive) through ACK against a shared mock cloud. The whole chain shows meaningful health in Argo CD because of the custom Lua checks. That is further than most "hub-spoke" labs get. The gaps are in *how* the platform is operated and secured. The platform controllers (kro, ACK, Traefik, and Argo CD itself) are installed with imperative scripts rather than GitOps. Production follows `main` of the app repo with no promotion gate. The CI pipeline overwrites release tags. The spokes have no network policy or Pod Security enforcement. A single unauthenticated Headlamp UI holds cluster-admin tokens for all three clusters. The docs describe several guardrails that are not actually implemented. The project also has a documentation drift problem: some docs still describe a `MessageProcessor` / `tenant-workloads` design that no longer exists.

**Maturity score: 5.5 / 10.** It is an excellent *architecture* sketch at about 7 and a solid learning lab, held back by *operational and security* posture at about 4. Most of the fixes are small and well-understood, and the lab is roughly two focused weekends away from a credible 7.5.

## 2. Strengths

- **A real multi-repo separation of concerns.** The control plane (AppSets and projects), the platform catalog (RGDs and controller config), the golden chart (OCI on GHCR), and the application (code plus per-env values) are separate repos with separate owners. This mirrors how real platform teams split things.
- **Health checks that mean something.** The Lua health checks for `kro.run/ResourceGraphDefinition`, `kro.run/*`, and `services.k8s.aws/*` (`clusters/values-argocd-hub.yaml`) make Argo CD's green actually reflect whether kro and ACK reconciled. Many production setups skip this.
- **A self-healing chain verified live.** kro reverted a manual `kubectl scale` on `orders-dev-worker` in under 5 s. Argo CD reverted a manual patch to the `QueueBackedService` spec in under 5 s. Both layers of the declarative chain do their job.
- **A well-designed RGD.** `queue-backed-service-rgd.yaml` has a correct dependency DAG (`dlq → queue → config → service/ingress → deployment`, confirmed in the RGD's `TOPOLOGICALORDER`), a DLQ with `RedrivePolicy` wired via CEL from the DLQ ARN, probes, resource requests and limits, `runAsNonRoot`, `allowPrivilegeEscalation: false`, and `drop: [ALL]`. It surfaces useful status (`queueURL`, `dlqARN`, `serviceURL`).
- **Tenant AppProject restricts cluster-scoped resources.** `tenant-workloads` may only create `Namespace` at cluster scope and only in `orders-*` or `tenant-*` namespaces. That is the correct instinct.
- **Spoke registration verifies TLS.** `register-spokes.sh` passes `caData` with `insecure: false`, so the hub-to-spoke connection is not trust-on-first-use.
- **Controllers and the golden chart are version-pinned.** kro `0.9.4`, ACK `1.7.1`, Headlamp `0.45.0`, and `queue-backed-service:1.0.0` are pinned.
- **Argo CD `exec.enabled=false`.** The chart's default NetworkPolicies are present in `argocd`.
- **The app image runs as non-root (UID 10001)** and matches the RGD's `securityContext`.
- **The Cluster generator uses an `environment` label** for blueprint distribution, so adding a third spoke requires only a label and no YAML changes.
- **Teardown is clean and idempotent**, and the Makefile provides a single entry point.

### Layer 2: Architecture and GitOps Maturity

### Layer 3: Operational Excellence and Extensibility

| # | Sev | Finding |
|---|---|---|
| L3-1 | **High** | **Out-of-band cloud drift is invisible for up to 10 hours, and everything stays green.** *Live test:* I deleted `orders-dev-dlq` directly in moto. After 120 s, the ACK Queue still reported `ResourceSynced=True`, kro reported `ACTIVE`, and Argo CD reported `Healthy`, while the main queue's `RedrivePolicy` pointed at a non-existent ARN. The cause is `RECONCILE_DEFAULT_RESYNC_SECONDS=36000`: ACK only re-reads AWS on a spec change or on resync, and an annotation does not trigger a reconcile because it does not change the generation. I restored the queue by restarting the ACK controller (recreated in 5 s, redrive intact). This is the most important lesson the lab can teach about ACK, and today it is hidden. |
| L3-2 | **High** | **moto state is ephemeral.** moto keeps state in memory. Any restart of the `moto-cloud` container (for example a WSL restart or Docker Desktop update) deletes every queue. Combined with L3-1, the whole platform will report Healthy against an empty cloud for hours. |
| L3-3 | Medium | **No metrics or alerting stack.** There is no Prometheus and no `ServiceMonitor` CRDs. The notifications controller is running, but `argocd-notifications-cm` has only a `context` block: no triggers, templates, or services. The kro and ACK controllers expose Prometheus metrics that nothing scrapes. `metrics-server` is the only telemetry. |
| L3-4 | Medium | **The smoke test gives false confidence.** (a) It never checks Argo CD Application sync or health, which is the most important GitOps signal. (b) `grep -c "Running" \|\| echo "0"` prints `0\n0` when there are no matches, which breaks the later `-ge` comparison. (c) If the workload check fails, it still prints "All Core Smoke Tests Passed!" because the `if` has no `else`/`exit 1`. (d) The expected-count comments (`test: 1`, `prod: 2`) are hard-coded and already disagree with the docs. |
| L3-5 | **High** | **Mutable release tags (supply chain and rollback).** `orders-processor/.github/workflows/ci.yaml` tags **every** push to `main` as `latest`, `v1.2.0`, **and `v1.1.0`**. A rollback to "v1.1.0" deploys whatever was built last, and with `imagePullPolicy: IfNotPresent`, different nodes can run different code under the same tag. Today all four pods share digest `sha256:f5db6552…`, but that is luck, not design. |
| L3-6 | Medium | **Version-pinning is inconsistent.** Pinned: kro, ACK, Headlamp, and the golden chart. There is no ring or wave rollout for the platform itself. |
| L3-7 | Medium | **No failure-mode sequencing.** There are no sync waves or `argocd.argoproj.io/sync-wave` annotations between blueprints and tenant apps. On a fresh cluster, tenant apps can sync before the RGD is `Active` and fail until retry. There is no `retry` block in any `syncPolicy`. |

### Layer 4: Security and Production Readiness

| # | Sev | Finding |
|---|---|---|
| L4-1 | **Critical (prod) / High (lab)** | **Headlamp is an unauthenticated cluster-admin gateway to all three clusters.** Its kubeconfig contains (a) a hub SA token bound to `cluster-admin`, and (b) the *same* `argocd-manager` tokens Argo CD uses for the spokes, which are also `cluster-admin`. It runs with `-insecure-ssl`, `insecure-skip-tls-verify: true` (even though the CA is available), and `-dev` (which relaxes CORS). It has no OIDC and is served on `0.0.0.0:8080`. Anyone who can reach port 8080 gets a web shell into prod. Because the tokens are shared with Argo CD, the audit log cannot tell the dashboard apart from the GitOps controller, and rotating one breaks the other. |
| L4-2 | **High** | **Argo CD authentication.** The only account is `admin`/`admin123`. Its bcrypt hash is committed to a public GitHub repo, which is equivalent to publishing the password. There is no SSO (Dex is running but unconfigured) and `policy.csv` is empty. The UI and API run over plain HTTP (`server.insecure`) on `0.0.0.0:8080`. |
| L4-3 | **High** | **Spokes have zero NetworkPolicies and no Pod Security Admission labels.** `orders-dev`, `orders-test`, and `orders-prod` can reach each other, `kube-system`, the ACK controller, and moto. Nothing enforces the `restricted` PSS. The RGD's `securityContext` would *fail* `restricted` today because it lacks `seccompProfile: RuntimeDefault`, so enabling enforcement is a real (and good) test. |
| L4-4 | **High** | **A single shared static AWS identity across environments.** Both spokes mount the same long-lived static key file from `platform-catalog/controllers/ack/credentials-secret.yaml`, committed to Git (mock values, but the *pattern* is committed), and both write into moto account `123456789012`. Prod and non-prod share one blast radius. ACK already runs with `--enable-carm=true`, so the per-namespace account mapping mechanism is available and unused. |
| L4-5 | Medium | **kro runs with `kro-cluster-role: */*[*]`,** which is effectively cluster-admin on each spoke. Any RGD merged into `platform-catalog` can create any resource on both spokes, including prod. The blueprint repo is therefore a cluster-admin-equivalent code path with no review gate, and it syncs to prod from `main`. |
| L4-6 | Medium | **The tenant AppProject is too broad at namespace scope.** It sets `namespaceResourceWhitelist: *:*`, so a tenant manifest can create `Role`/`RoleBinding` (including binding the `cluster-admin` ClusterRole in its namespace), raw ACK resources that bypass the golden path, `Secret`s of type SA-token, and so on. The Argo CD destination SA is `cluster-admin`, so nothing downstream stops it. There are no `sourceNamespaces`, no project `roles`, no `syncWindows`, and no `orphanedResources` monitoring. |
| L4-7 | Medium | **The `default` AppProject is wide open** (`*` repos, `*` destinations, `*` cluster resources). Any Application that omits `project:` bypasses every guardrail above. Lock it to empty. |
| L4-8 | Medium | **Supply chain.** There is no image scanning (Trivy/Grype), no signing (cosign/Sigstore), no SBOM, and no admission verification (Kyverno/Connaisseur). GitHub Actions are pinned by tag rather than SHA. Deployments reference tags, not digests. Combined with L3-5, it is impossible to prove what runs in prod. |
| L4-9 | Medium | **Local control-plane exposure.** Ports `8080` (Argo CD and Headlamp), `8081`, `8082`, `8443`, `5000` (moto, unauthenticated, including `/moto-api/reset`), and the three kube-apiservers are all bound to `0.0.0.0`. On default WSL2 NAT this is mostly contained to the Windows host, but mirrored networking or a `netsh portproxy` would expose it to the LAN. Bind to `127.0.0.1` explicitly. |
| L4-10 | Low | **Long-lived SA-token Secrets** (`kubernetes.io/service-account-token`) are used for `argocd-manager` and `headlamp`. They never expire. This is fine for a lab, but it is the pattern EKS access entries and Pod Identity exist to replace. |
| L4-11 | Low | **Workload pods use the namespace `default` ServiceAccount** with an auto-mounted token. There is no `readOnlyRootFilesystem`, no PDB, and no HPA. |

## 4. Prioritized Recommendations

### Quick wins (under 1 hour each)

1. **Fix the CI tagging** (`orders-processor/ci.yaml`). Tag only with `type=sha` and `type=semver` on `v*` git tags. Drop the hard-coded `v1.2.0`/`v1.1.0`/`latest`. Derive `APP_VERSION` from the tag. *Learning:* immutable artifacts are the foundation of rollback. *Prod:* this is a supply-chain integrity control. **Effort: S.**
2. **Make the smoke test honest.** Assert that `argocd app list` (or `kubectl get applications`) is all `Synced/Healthy`. Assert that each `QueueBackedService` is `ACTIVE`. Assert that each queue *and* DLQ exists in moto via `get-queue-url`. `exit 1` on any failure. Fix the `grep -c` bug. **Effort: S.**
3. **Clean up stale state.** Delete the `messageprocessors.kro.run` CRD on both spokes, archive the `tenant-workloads` repo and remove it from the AppProject/README/diagram, remove the stray Headlamp containers, and delete the manual `repo-ghcr-charts` secret. **Effort: S.**
4. **Lock down the `default` AppProject** (`sourceRepos: []`, `destinations: []`, no cluster whitelist). **Effort: S.**
5. **Bind every host port to `127.0.0.1`** (`--port "127.0.0.1:8080:80@loadbalancer"`, `-p 127.0.0.1:5000:5000`, `--api-port 127.0.0.1:0`). **Effort: S.**
6. **Lower the ACK resync** to `RECONCILE_DEFAULT_RESYNC_SECONDS=300` in `values-sqs.yaml` (`reconcile.defaultResyncPeriod`). Then rerun the DLQ-deletion experiment and document it as a lab exercise. *Learning:* this shows how ACK actually detects cloud drift. *Prod:* you choose the resync period deliberately, trading API cost against drift window. **Effort: S.**
7. **Add `seccompProfile: {type: RuntimeDefault}`** and `readOnlyRootFilesystem: true` (with an `emptyDir` for `/tmp`) to the RGD Deployment, and a dedicated ServiceAccount with `automountServiceAccountToken: false`. **Effort: S.**
8. **Update the stale docs** (the tutorial's kind, app names, replica counts, repo count, `/home/bleite` paths, prompt link). **Effort: S–M.**

### Medium effort (half a day to a day each)

9. **Move the platform layer into GitOps (the most important change).** Create `addons/` ApplicationSets in `gitops-control-plane`: a Cluster generator (label `platform.kro/enabled=true`) × a List of addons `{kro 0.9.4, ack-sqs 1.7.1, traefik x.y.z}`, each a Helm source with `$values` from `platform-catalog/controllers/<addon>/values.yaml`. Add a self-managed `argo-cd` Application and have `root-control-plane` also sync `projects/`. `setup-hub-spoke.sh` then shrinks to "create clusters, install Argo CD once, apply the root app". *Learning:* this is the core pattern of EKS Blueprints / GitOps Bridge. *Prod:* controller upgrades become PRs, drift is visible, and a new spoke is a label. **Effort: M.**
10. **Implement the promotion gate you already documented.** Point `orders-prod` at a release tag or an `env/prod` branch rather than `main`. Add `CODEOWNERS` for `deploy/values-prod.yaml`. Give the `tenant-workloads` project a `syncWindows` entry (`kind: deny` for prod outside business hours, `manualSync: true`) and a `prod-deployer` role. Do the same for `platform-catalog`: split into `kro-blueprints-nonprod` (tracks `main`) and `kro-blueprints-prod` (tracks a tag). **Effort: M.**
11. **Replace Headlamp's credentials.** Give it its own ServiceAccount per cluster bound to the built-in `view` ClusterRole (not `cluster-admin`, not Argo CD's token). Use the spoke CA instead of `insecure-skip-tls-verify`. Try removing `-dev` by serving Headlamp on the same origin (e.g. `localhost:8080/headlamp` with `baseURL`) rather than suppressing CORS. **Effort: M.**
12. **Harden the RGD schema.** For example `environment: string | enum="dev,test,prod"`, `replicas: integer | default=1 minimum=1 maximum=10`, `messageRetentionPeriod: string | default="345600"`. Derive queue names from `schema.metadata.namespace` + `schema.metadata.name`. Move `MOTO_ENDPOINT` and the ingress port to a per-cluster ConfigMap read via `externalRef`. Add a `NetworkPolicy` and a `PodDisruptionBudget` to the graph. Add a `readyWhen` on the Deployment. **Effort: M.**
13. **Network and Pod Security baseline on the spokes.** Label the `orders-*` namespaces `pod-security.kubernetes.io/enforce=restricted`. Add a default-deny NetworkPolicy plus explicit allows (ingress from Traefik, egress to DNS and `moto-cloud`). Note that k3s ships with a NetworkPolicy controller, so these are actually enforced. **Effort: M.**
14. **Persist moto and separate accounts.** Run moto with `MOTO_ENABLE_RECORDING`/state persistence, or add a moto `init` that is idempotent. Use CARM (`--enable-carm` is already on): an `ack-role-account-map` ConfigMap mapping `orders-prod` → account `222222222222` and nonprod → `111111111111`, with namespace annotation `services.k8s.aws/owner-account-id`. moto partitions state by account ID, so you get genuine prod and non-prod cloud isolation locally. **Effort: M.**
15. **ApplicationSet modernization.** Collapse the two tenant AppSets into one with `goTemplate: true`, `missingkey=error`, and a matrix of a Git-files generator (`orders-processor/deploy/*/config.json` or a tenants registry) × a Cluster generator selected by `environment`. Add `syncPolicy.retry` with backoff, and sync waves (blueprints wave −1). **Effort: M.**

### Strategic (multi-day)

16. **Observability stack as an addon.** Install `kube-prometheus-stack` on the hub, or Prometheus agent on the spokes with remote-write to the hub. Add ServiceMonitors for Argo CD, kro, and ACK, and alerts for `argocd_app_info{health_status!="Healthy"}`, ACK `ResourceSynced=False`, and kro instance `Ready=False`. Configure Argo CD notifications (`on-sync-failed`, `on-health-degraded`) to a webhook. **Effort: L.**
17. **SSO and RBAC.** Run Keycloak or Dex with a GitHub connector as a hub addon. Define Argo CD groups `platform-admins`, `tenant-a-devs` (sync non-prod only), and `release-managers` (prod), and disable `admin`. Tenant project `roles` scoped to `orders-*` apps. **Effort: L.**
18. **Least-privilege spoke access.** Replace the `argocd-manager` `cluster-admin` binding with an aggregated role limited to what the AppProjects allow, or use Argo CD's `application.sync.impersonation.enabled` (already present in `argocd-cm`) with a per-project destination ServiceAccount. Constrain kro RBAC (check the chart's aggregation/limited-RBAC mode for 0.9.x) and the tenant `namespaceResourceWhitelist` to the kinds the golden chart actually emits (`kro.run/QueueBackedService`, plus maybe `ConfigMap`). **Effort: L.**
19. **Supply-chain pipeline.** Pin Actions by SHA. Add Trivy with fail-on-HIGH, cosign keyless signing, and an SBOM attestation. Add Kyverno `verifyImages` on the spokes restricted to `ghcr.io/brunobml/*`, and have the golden chart render `image@sha256:`. Automate promotion (Kargo or Argo CD Image Updater writing to Git). **Effort: L.**
20. **Policy as code.** Kyverno or ValidatingAdmissionPolicy on the spokes: require the `restricted` PSS, require labels, block raw `sqs.services.k8s.aws/Queue` outside the golden path, and require the `deletion-policy: retain` annotation in prod. **Effort: M–L.**

## 5. Production Parity Gap Analysis

| Concern | What this lab currently does | What a real EKS hub-spoke platform (Argo CD + kro + ACK) needs |
|---|---|---|
| Cluster provisioning | k3d via bash, unpinned k3s | Terraform/eksctl/ACK-EKS or Crossplane; pinned EKS versions; managed node groups or Karpenter |
| Spoke registration | Long-lived SA token + CA in a Secret, `cluster-admin` | EKS Access Entries + Argo CD `awsAuthConfig` (IRSA/Pod Identity role assumed by the hub); scoped access policy; cluster Secrets generated by Terraform/GitOps Bridge with metadata annotations |
| Addon lifecycle | `helm install` from a script | Addons ApplicationSet (Cluster gen × addon list), version per env/cluster label, progressive rollout by label rings |
| Argo CD lifecycle | Helm from script, unpinned | Self-managed Argo CD Application, HA mode (redis-ha, 2+ repo-servers, sharded controllers), or the managed EKS Argo CD capability |
| AWS credentials for ACK | Static key file in a Secret, shared across envs | EKS Pod Identity / IRSA per controller, per spoke, per account; CARM/IAMRoleSelector for per-namespace accounts; no static keys anywhere |
| AWS account model | One moto account for prod + non-prod | Separate AWS accounts (Organizations) per env, and often per tenant; SCPs; resource tagging enforced |
| Cloud drift | 10 h resync; delete-by-default | Tuned resync (minutes to 1 h); `deletion-policy: retain` for stateful prod resources; `adopt` for imports; CloudTrail/Config as a second drift signal |
| Authn/Authz (humans) | `admin/admin123`, hash in public Git, HTTP | SSO (IAM Identity Center/Okta via OIDC), Argo CD RBAC groups, admin disabled, TLS via ACM + ALB, private endpoint or VPN |
| Promotion | All envs track `main`, auto-sync prod | Release tags/branches or Kargo; sync windows; CODEOWNERS on prod values; manual or gated prod sync; separate platform-catalog rings |
| Multi-tenancy | One AppProject for all tenants, `*:*` namespaced kinds | AppProject per tenant, `sourceNamespaces` (apps-in-any-namespace), destination SA impersonation, namespace-scoped kinds limited to the golden path, ResourceQuota/LimitRange per namespace |

## 6. Onboarding & Learnability Score

**6 / 10.** The *intent* is exceptionally well-explained. The mermaid diagrams, the "why Headlamp + Argo CD" table, the Well-Architected mapping, and the promotion-patterns doc are better than most internal platform docs. What lowers the score is that a new engineer who follows `docs/developer-tutorial.md` will hit things that don't exist (`MessageProcessor`, `tenant-a-*` apps, 5 prod replicas), will be told to push 3 repos when 5 exist, and will run a smoke test that says "passed" regardless of workload state.

Concrete suggestions:

1. **Add one "Request flow" page:** *commit to `orders-processor/deploy/values-dev.yaml` → Argo CD `orders-dev` renders `queue-backed-service:1.0.0` → `QueueBackedService/orders` → kro DAG → ACK `Queue` ×2 → moto → ConfigMap → Deployment*, with the exact `kubectl get` command to observe each hop. This is the mental model everything else hangs on.
2. **Add a `REPOS.md` (or a README table)** listing the 5 repos, what each owns, who would own it in a real org, and which Argo CD Application consumes it.
3. **Turn the drift experiments into guided labs:** "Lab 3: delete a queue in moto and watch nothing happen; then lower resync". Failure-driven exercises teach more than happy paths.
4. **Add `make doctor`** to check prerequisites (`docker`, `k3d`, `helm`, `kubectl`, `jq`, `aws`), sibling repo presence, and free ports before `make setup`.
5. **Fold `make bootstrap` into `make setup`,** or print it as a loud final "NEXT STEP". Replace absolute paths with `$(REPOS_DIR)`.
6. **Mark aspirational docs clearly.** `production-promotion-guardrails.md` and `lab-progression-and-next-steps.md` should carry a status banner ("Implemented" / "Design only") so a reader doesn't assume the guardrails exist.
7. **Add an ADR folder** (`docs/adr/`) for decisions like "golden chart wraps kro instance" and "app repo owns env values", including their trade-offs.

## 7. Final Architect's Verdict

You have built the hard part. A working, three-cluster GitOps chain with kro composing ACK resources into a meaningful platform API (queue, DLQ, redrive, config injection, workload), with health that flows correctly back to Argo CD, is not trivial, and the self-healing works. The repository split and the golden-chart-over-RGD layering show that you understand how platform teams actually divide ownership.

What separates this from a production platform is not more features. It is **turning the platform on itself**. Right now GitOps manages the *tenants*, but a script manages the *platform*. Make the hub own kro, ACK, Traefik, AppProjects, and Argo CD through the same ApplicationSet machinery you already use for workloads. That one change fixes reproducibility, upgrades, drift visibility, and spoke onboarding at once. Then make the *controls you've already designed on paper* real: promotion gates, immutable images, least privilege, network policy. Your docs show you know what good looks like. The next step is closing the gap between the documents and the running system, and running the uncomfortable experiments (like deleting a DLQ behind ACK's back) that show where the green checkmarks lie.

Do the eight quick wins this week and recommendation 9 next. At that point this becomes a lab I would hand to a new platform engineer on day one.
