### Finding L1-2: Orphaned CRD `messageprocessors.kro.run` on Spokes

* **Assessment Finding**: When the platform blueprint transitioned from `MessageProcessor` to `QueueBackedService` (`platform-catalog@4987050`), the old ResourceGraphDefinition (RGD) was deleted. However, Kubernetes CustomResourceDefinitions (CRDs) generated by kro are not automatically garbage-collected. The stale CRD remains registered on both `k3d-spoke-nonprod` and `k3d-spoke-prod`.
* **Action Plan**:
  ```bash
  # 1. Verify zero active instances exist on nonprod and prod spokes
  kubectl --context k3d-spoke-nonprod get messageprocessors.kro.run -A
  kubectl --context k3d-spoke-prod get messageprocessors.kro.run -A

  # 2. Safely delete the orphaned CRD from both workload clusters
  kubectl --context k3d-spoke-nonprod delete crd messageprocessors.kro.run
  kubectl --context k3d-spoke-prod delete crd messageprocessors.kro.run
  ```
* **What We Agree With**:
  - Deprecated CRDs pollute `kubectl api-resources`, confuse platform consumers, and permit applying obsolete manifests without API schema validation errors.
  - Live inspection confirmed **zero active instances** on both clusters; deletion will not cause pod disruption or resource loss.
* **Concerns & Nuances**:
  - *Documentation Coupling*: `docs/developer-tutorial.md` still teaches developers how to deploy `kind: MessageProcessor`. If the CRD is deleted before the tutorial is updated, anyone running the tutorial will face immediate admission rejection (`the server doesn't have a resource type "MessageProcessor"`).
  - *Resolution*: Deleting the CRD must be accompanied by updating `docs/developer-tutorial.md` to reference `QueueBackedService`.

### Finding L1-6: Hard-Coded Personal Paths (`/home/bleite/...`)

* **Assessment Finding**: Absolute filesystem paths (`/home/bleite/repos/...`) are hardcoded in the `Makefile` (`build-app`), root `README.md` command examples (`cd /home/bleite/repos/...`), and several documentation links (`file:///home/bleite/...`). This breaks clone-and-run portability for any other platform engineer.
* **Action Plan**:
  1. **Update `Makefile`**:
     Replace absolute repo references with relative path resolution based on `CURDIR`:
     ```makefile
     REPOS_DIR ?= $(abspath $(CURDIR)/..)
     ORDERS_DIR ?= $(REPOS_DIR)/orders-processor

     build-app:
     	@bash $(ORDERS_DIR)/build-and-push.sh $(TAG)
     ```
  2. **Update Root `README.md`**:
     Replace `cd /home/bleite/repos/<repo>` with standard relative shell navigation:
     ```bash
     cd ../platform-catalog
     git push -u origin main
     ```
  3. **Update Markdown Links**:
     Convert absolute `file:///home/bleite/repos/...` links into standard GitHub relative markdown links (e.g. `[addon-headlamp.yaml](../applicationsets/addon-headlamp.yaml)`).
* **What We Agree With**:
  - A core principle of open-source platform engineering labs is portability across developer environments (Linux, macOS, WSL2).
* **Concerns & Nuances**:
  - *Multi-Repo Layout Dependency*: The Makefile targets assume all 5 repositories (`gitops-control-plane`, `platform-catalog`, `platform-charts`, `orders-processor`, `tenant-workloads`) are cloned into the same parent workspace directory. If a user clones them into arbitrary detached folders, relative paths still break.
  - *Mitigation*: Provide an overridable `REPOS_DIR` environment variable in the `Makefile` with a sensible default: `REPOS_DIR ?= $(shell dirname $(CURDIR))`.

### Finding L2-7: Duplicate Helm Repo Credentials Secret in Argo CD

* **Assessment Finding**: Both `argocd-repo-ghcr-charts` (declared in Helm values `clusters/values-argocd-hub.yaml`) and `repo-ghcr-charts` (created manually via `kubectl create secret`) exist in the `argocd` namespace for the exact same OCI URL (`ghcr.io/brunobml/charts`).
* **Action Plan**:
  1. Verify the declarative secret `argocd-repo-ghcr-charts` contains valid credentials:
     ```bash
     kubectl --context k3d-hub-cluster -n argocd get secret argocd-repo-ghcr-charts -o yaml
     ```
  2. Test deleting the unmanaged imperative secret:
     ```bash
     kubectl --context k3d-hub-cluster -n argocd delete secret repo-ghcr-charts
     ```
  3. Force hard refresh on the tenant applications (`orders-dev`, `orders-test`, `orders-prod`) to confirm Argo CD's repo-server pulls the golden chart (`oci://ghcr.io/brunobml/charts/queue-backed-service:1.0.0`) without authentication errors.
* **What We Agree With**:
  - Having multiple secrets for the same repository creates split-brain confusion and violates GitOps single-source-of-truth principles.
* **Concerns & Nuances**:
  - *Public vs Authenticated OCI*: If `ghcr.io/brunobml/charts` is public, no authentication secret is strictly required, but Argo CD logs rate-limit warnings if anonymous. If private, deleting the manual secret could break chart rendering if the declarative secret is missing the `enableOCI: "true"` or `type: "helm"` data keys.
  - *Validation Guard*: Inspect secret keys before deletion to ensure `argocd-repo-ghcr-charts` matches Argo CD's required schema (`type: helm`, `enableOCI: "true"`, `url: ghcr.io/brunobml/charts`).

### Finding L3-8: Extensibility / Imperative ACK Controller Installation

* **Assessment Finding**: Adding a new ACK service controller (e.g. DynamoDB, S3) requires manually editing `scripts/setup-hub-spoke.sh` and running Helm imperatively, rather than declaring it as an entry in an ApplicationSet.
* **Action Plan**:
  - In the short term, ensure `setup-hub-spoke.sh` is cleanly parameterized with an extensible array of ACK services:
    ```bash
    ACK_SERVICES=("sqs")
    for svc in "${ACK_SERVICES[@]}"; do
      helm upgrade --install "ack-${svc}-controller" ...
    done
    ```
  - In the medium term (Recommendation 9 / Layer 2-1), migrate all platform controllers (kro, ACK SQS, Traefik) into an `addons/` ApplicationSet.
* **What We Agree With**:
  - The assessment is correct that GitOps should ideally manage the platform controllers, not just tenant applications.
* **Concerns & Nuances**:
  - *Severity Classification*: The assessment lists this as **Low** in Layer 3, but elevated it to **Recommendation 9 (Effort: M)** in the strategic roadmap.
  - *Chicken-and-Egg Lifecycle*: Controllers like kro and ACK require initial cluster secrets (such as AWS credentials and CRDs) before they can run. Moving them prematurely into GitOps without a solid bootstrap order (sync waves -1) can lead to bootstrap race conditions.
  - *Recommendation*: Address this iteratively—first standardize the script interface, then move to ApplicationSets in Phase 2.

### Finding L4-10: Long-Lived ServiceAccount Token Secrets

* **Assessment Finding**: `argocd-manager` and `headlamp` rely on static, long-lived `kubernetes.io/service-account-token` Secrets that never expire.
* **Action Plan**:
  - Document this explicitly in [`docs/aws-well-architected-production-guide.md`](file:///home/bleite/repos/gitops-control-plane/docs/aws-well-architected-production-guide.md) under Security Pillar as an **Accepted Lab Trade-off for Local k3d**.
  - Document the exact EKS production pattern:
    1. **EKS Access Entries**: Granting IAM principals direct cluster access without static Kubernetes tokens.
    2. **Argo CD Spoke Assumed Roles**: Hub Argo CD assumes an IAM role (`arn:aws:iam::ACCOUNT:role/ArgoCDSpokeExecutionRole`) using EKS Pod Identity / IRSA.
    3. **TokenRequest API**: Bound ServiceAccount tokens with short TTLs (1 hour) projected into pods.
* **What We Agree With**:
  - In AWS EKS production environments, static long-lived SA token secrets are a security vulnerability (non-expiring, manual revocation required, susceptible to exfiltration).
* **Concerns & Nuances**:
  - *Lab Feasibility*: **We strongly advise against attempting to replace static SA tokens in this local k3d lab.**
  - *Why?* Local k3d has no native integration with AWS IAM or EKS Access Entries. Emulating token rotation locally requires either:
    1. Running an external cert-manager and HashiCorp Vault daemon to rotate kubeconfigs every 60 minutes, or
    2. Modifying Argo CD to execute continuous TokenRequest calls against remote spoke APIs.
  - This introduces enormous operational overhead that detracts from the core learning objectives of GitOps, kro composability, and ACK cloud orchestration.
  - *Decision*: **Accept as a documented design divergence between local development and AWS EKS.**

### Finding L4-11: Workload Pod Hardening (ServiceAccount, PSS Restricted, PDB, HPA)

* **Assessment Finding**:
  1. Workload pods in `orders-*` mount the namespace `default` ServiceAccount token automatically.
  2. Pods lack `seccompProfile: {type: RuntimeDefault}`, failing the Kubernetes `restricted` Pod Security Standard.
  3. Containers do not enforce `readOnlyRootFilesystem: true`.
  4. Workloads lack `PodDisruptionBudget` (PDB) and `HorizontalPodAutoscaler` (HPA).
* **Action Plan**:
  1. **Update Kro Platform Blueprint (`queue-backed-service-rgd.yaml`)**:
     - **Add Dedicated ServiceAccount**: Generate a dedicated `ServiceAccount` with `automountServiceAccountToken: false` for each worker instance.
     - **Add Seccomp Profile**: Add `seccompProfile: {type: RuntimeDefault}` to the pod security context.
     - **Add Read-Only Root Filesystem**:
       ```yaml
       securityContext:
         readOnlyRootFilesystem: true
         allowPrivilegeEscalation: false
         capabilities:
           drop: [ALL]
       volumeMounts:
         - name: tmp
           mountPath: /tmp
       volumes:
         - name: tmp
           emptyDir: {}
       ```
     - **Add Environment Variable**: Set `PYTHONDONTWRITEBYTECODE=1` in `orders-processor` deployment spec to ensure Python does not attempt to write `.pyc` files to disk.
  2. **Add Optional PodDisruptionBudget**:
     Add a PDB to the Kro blueprint, active only when `replicas > 1`:
     ```yaml
     apiVersion: policy/v1
     kind: PodDisruptionBudget
     metadata:
       name: ${schema.spec.name}-${schema.spec.environment}-pdb
     spec:
       minAvailable: 1
       selector:
         matchLabels:
           app: ${schema.spec.name}-${schema.spec.environment}-worker
     ```
* **What We Agree With**:
  - Workload pods processing SQS messages have zero requirement to query the Kubernetes API; disabling the token mount eliminates a primary lateral movement vector.
  - Complying with `restricted` PSS is a best practice.
* **Concerns & Nuances**:
  - *ReadOnly Filesystem Breakage*: Python applications frequently fail with `readOnlyRootFilesystem: true` if:
    1. Python attempts to write cached bytecode (`.pyc`) to the application directory.
    2. Logging frameworks attempt to write log files locally.
    3. The application runtime relies on `/tmp` for scratch state.
  - *Required Safeguard*: In addition to `emptyDir` on `/tmp`, we must ensure `PYTHONDONTWRITEBYTECODE: "1"` is passed to prevent runtime exceptions.
  - *PDB on Single-Replica Workloads*: In `dev` (`replicas: 1`), setting `minAvailable: 1` prevents node drains (`kubectl drain` will hang indefinitely). The PDB must either use `maxUnavailable: 1` or be conditionally rendered when `replicas >= 2`.
  - *HPA vs Queue Scaling*: Standard HPA based on CPU/Memory is inappropriate for SQS workers (waiting on an empty queue uses 0% CPU; processing 1000 messages may still use minimal CPU). Queue depth scaling via KEDA (as planned in Track 1) is the correct architectural pattern.
